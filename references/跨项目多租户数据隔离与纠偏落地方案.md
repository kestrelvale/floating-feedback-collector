# 跨项目多租户数据物理隔离与一键纠偏落地指南 (V3.2.0)

> **文档定位**: 专用于解决多个不同业务项目（如人力资源 `project-a` vs 社区生鲜 `project-b`）共用服务器或接入套件时发生的**数据串门、业务工单混淆与终端 UI 硬编码**等致命缺陷。  
> **核心机制**: 基于 `projectId` 的多租户数据库物理隔离、前端零污染初始化与自适应多端动态渲染引擎。

## 1. 致命问题根因剖析 (为什么会串到人力资源项目？)

在新项目（如 `project-b`）打开 `feedback-dashboard.html` 却看到 `project-a`（项目 A（人力资源））的 28 条求职/面试工单与五端分类，根因有三：

1. **API 未做项目命名空间隔离 (No Project Namespace)**:
   - 线上服务器上的 `/api/feedback/list` 之前只维护了一套全局默认数据库；当 `project-b` 去请求云端接口时，接口直接返回了原本属于 `project-a` 的工单；
2. **初始化模板夹带历史脏数据 (Seed Data Contamination)**:
   - 套件模板库中的 `templates/server/feedback_database.json` 之前包含了项目 A的 28 条工单与五端映射，初始化时直接复制到了新项目中；
3. **中台 UI 硬编码了项目 A 的五端 (Hardcoded Terminals)**:
   - `feedback-dashboard.html` 内部此前硬编码了“项目 A 的五端（求职端/经纪人端/B端企业小程序/B端Web后台/平台运营端）”，未能根据新项目的实际终端动态自适应渲染。

## 2. 多租户数据物理隔离三大铁律架构

为了保证**“就算 100 个项目部署在同一个服务器上，数据也 100% 绝对隔离，互不相干”**，V3.2.0 确立以下隔离规范：

```
┌────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│ 🌟 多项目多租户数据物理隔离架构 (Multi-Tenant Project Data Isolation)                                │
├────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ 1. 🏷️ 项目专属身份标识 (Project Identity):                                                            │
│    • 每个项目自动提取或分配唯一的 `projectId` (如 `project-b` vs `project-a`)；                │
│    • 所有 API 请求强制携带 `?projectId=${projectId}`；                                                │
│                                                                                                        │
│ 2. 🗄️ 服务端独立数据库物理隔离 (Database File Isolation):                                              │
│    • 服务端根据 `projectId` 自动分库落盘：                                                            │
│      - 项目 A (`project-a`): 存入 `data/feedback_database.json`                                   │
│      - 项目 B (`project-b`): 存入 `data/feedback_database_project-b.json`                       │
│    • 不同项目的数据物理隔离，绝不查询对方的数据表！                                                   │
│                                                                                                        │
│ 3. 📱 中台 UI 与终端网格 100% 自适应动态渲染:                                                          │
│    • 中台大标题自动显示当前项目名称（如 `project-b · 原型反馈与 Agent 闭环排障中枢`）；             │
│    • 终端分类网格不再硬编码项目 A 的五端，而是完全根据当前项目自身的 `urlMappings` 动态生成！               │
│                                                                                                        │
│ 4. 🧹 新项目初始化纯净底座:                                                                            │
│    • 新项目初始化时，`feedbacks: []` 必须是 100% 纯净空列表，零历史数据污染。                         │
└────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 3. 一键更正与数据隔离落地提示词 (Correction Prompt)

> **使用方法**: 直接将以下整段 Markdown 提示词复制，发送给出现数据串门的目标项目 Agent（例如在 `project-b` 会话中执行）。Agent 会立即清除错误挂接的人力资源数据，以当前项目的独立 `projectId` 建立专属纯净数据库，并自动映射当前项目的真实页面：

```markdown
【🚨 跨项目数据隔离与专属中枢重构令 · P0 优先级】

当前项目的反馈中枢错误挂接到了人力资源系统（项目 A）的数据源上，导致数据串门与终端名称错误。现发布最高优先级更正令，请立即按照【多租户数据物理隔离标准】重构当前项目的反馈与排障中枢：

================================================================================
【📌 当前项目专属身份与隔离配置区】:
- 项目唯一标识   [PROJECT_ID]:   project-b (用于服务端数据库物理隔离)
- 项目业务名称   [PROJECT_NAME]: project-b (商城与配送业务)
- 业务系统前端   [BUSINESS_URL]: http://localhost:5300/ (严禁占用此端口)
- 线上服务器地址 [REMOTE_URL]:   https://your-domain.com
- 排障中台独立端口 [HUB_PORT]:   25300 (与业务端口 5300 物理隔离)
- 官方 Git 代码仓库 [GIT_REPO]:   https://github.com/kestrelvale/floating-feedback-collector.git
================================================================================

### 🛠️ 必须执行的 4 步数据隔离更正动作:

#### 第一步：物理清除被错误引入的旧项目数据与映射
请执行以下清理，彻底切除外来人力资源项目数据污染：
```bash
echo "==> 1. 正在清理旧项目的混流数据..."
rm -f data/feedback_database.json 2>/dev/null || true
```

#### 第二步：从官方仓库拉取最新 V3.2.0 多租户隔离套件
```bash
SKILL_DIR="$HOME/.codex/skills/floating-feedback-collector"
if [ -d "$SKILL_DIR/.git" ]; then
  cd "$SKILL_DIR" && git fetch origin && git reset --hard origin/main
else
  mkdir -p "$HOME/.codex/skills"
  git clone "$GIT_REPO" "$SKILL_DIR"
fi
```

#### 第三步：使用当前项目专属 PROJECT_ID 初始化独立纯净中枢
```bash
node "$SKILL_DIR/cli/init.js" \
  --mode=online \
  --target=. \
  --port=25300 \
  --remote-url="https://your-domain.com" \
  --inject \
  --mcp \
  --yes
```
执行后确认：
1. `data/feedback_database.json` 中的 `projectId` 已标记为 `project-b`，`feedbacks: []` 为 100% 纯净空表（0 条旧人力资源工单）；
2. `data/feedback_database.json` 中的 `urlMappings` 是根据当前项目实际扫描出来的页面（如 `o2o/`、`test_category.html` 等），零项目 A 的五端残留；
3. `feedback-dashboard.html` 标题已更新为 `project-b · 原型反馈与 Agent 闭环排障中枢`；
4. `feedback-dashboard.html` 与 `mcp/feedback-service.js` 中的请求全部携带 `projectId=project-b`。

#### 第四步：重启当前项目独立排障服务并执行端到端自验
```bash
bash scripts/stop.sh 2>/dev/null || true
bash scripts/start.sh
bash scripts/status.sh
```
运行自验，确认满足以下门禁：
- **门禁 ① 纯净度验证**: 访问 `curl -s "http://127.0.0.1:25300/api/feedback/summary?projectId=project-b"` 确认 `total: 0, pending: 0`；
- **门禁 ② 页面无串门**: 打开 `http://127.0.0.1:25300/feedback-dashboard.html`，确认大盘标题为当前项目名称，中台无任何“求职者/经纪人”等项目 A业务工单；
- **门禁 ③ 业务端口隔离**: 确认业务系统 `http://localhost:5300/` 正常运行，未被排障服务抢占。

#### 第五步：输出规范纠偏交付汇报
完成后输出四状态机看板与提请验收卡，给出当前项目独立的本地中台访问地址 `http://127.0.0.1:25300/feedback-dashboard.html`。
```

## 4. 项目数据隔离前后对比与验收标准

| 维度 | 纠偏前 (错误状态) | 纠偏后 (V3.2.0 物理隔离标准) |
| :--- | :--- | :--- |
| **数据源归属** | 错误混入 `project-a` 的 28 条求职/面试工单 | 100% 仅归属于 `project-b` 的纯净独立数据库 |
| **页面位置映射** | 映射为项目 A“求职端/经纪人端/B端Web后台” | 自动自学习映射为当前项目的真实文件 (如 `o2o/...`) |
| **中台界面呈现** | 显示“项目 A · 五端排障中枢” | 显示当前项目专属标题与自适应终端分类 |
| **服务端隔离机制** | 所有项目共用同一张全局列表 | 通过 `projectId` 命名空间分库分表存储，互不相干 |
| **端口占用机制** | 抢占项目的开发端口 5300 | 自动分配 `25300` 独立辅助端口，业务端口完全自由 |
